## Kết quả triển khai

- [AuthService](../../backend/src/main/java/com/dormtrading/iam/auth/AuthService.java): đăng ký, OTP, login/me, refresh xoay vòng, logout từng phiên, đổi/reset mật khẩu; PostgreSQL transaction và advisory lock serialize thao tác cùng email. Thất bại nghiệp vụ vẫn lưu bộ đếm/replay revocation.
- [SecurityConfig](../../backend/src/main/java/com/dormtrading/iam/SecurityConfig.java): bỏ JWT fallback, kiểm chữ ký/issuer/exp; kiểm phiên và quyền hiện tại từ DB ở mỗi request. Access 15 phút, session/refresh có hạn tuyệt đối 30 ngày. Không chờ JWT hết hạn khi thu hồi.
- [V3](../../backend/src/main/resources/db/migration/V3__authentication.sql): xác minh email và duyệt hồ sơ riêng, phiên/refresh family/challenge/reset grant/bộ đếm/thông báo; [V4](../../backend/src/main/resources/db/migration/V4__otp_delivery_outbox.sql): hàng đợi SMTP. Tài khoản cũ không tự được đánh dấu đã xác minh/duyệt. Tài khoản mới có điểm 0, P1-02 chịu trách nhiệm kích hoạt và khởi tạo 100 một lần.
- [PasswordPolicy](../../backend/src/main/java/com/dormtrading/iam/auth/PasswordPolicy.java): 15–128 Unicode code point sau NFC, giữ khoảng trắng; Argon2id 19 MiB/2 lượt/1 luồng; chặn giá trị dễ đoán và kiểm HIBP bằng tiền tố SHA-1, không gửi mật khẩu hoặc full hash. Khi dịch vụ kiểm tra lỗi, từ chối tạo/đổi mật khẩu bằng 503; không bỏ qua kiểm tra ở runtime.
- [OtpDelivery](../../backend/src/main/java/com/dormtrading/iam/auth/OtpDelivery.java): SMTP ngoài request quên mật khẩu, hàng đợi mã hóa AES-GCM và ràng buộc challenge bằng AAD. Retry mỗi 3 giây trong hạn mã; không gửi mã đã dùng/hết hạn; xóa payload sau gửi. Response chỉ xác nhận yêu cầu, không khẳng định email đã được giao. Thông báo đổi mật khẩu có outbox retry riêng.
- Mobile: đăng ký/xác minh/quên/đổi mật khẩu, hiện/ẩn mật khẩu, cooldown gửi lại; SecureStore cho hai token; hồ sơ đọc/sửa họ tên và trạng thái chờ duyệt. Web: đăng nhập/khôi phục/đổi/reset/logout; access trong bộ nhớ, refresh cookie Secure/HttpOnly/SameSite=Strict. Single-flight refresh trong mỗi client, web thêm Web Locks giữa tab khi trình duyệt hỗ trợ.
- [PublicListingsController](../../backend/src/main/java/com/dormtrading/catalog/PublicListingsController.java): đọc tối đa 100 tin công khai/trang để người chờ duyệt lướt sàn, không trả email/MSSV/hash hoặc tin nháp. Đây là phần đọc tối thiểu; tìm kiếm/đăng và sửa tin đầy đủ thuộc Phase 2.

## Hợp đồng API hiện hành

Base path `/api/v1`. POST nhận JSON. Lỗi nghiệp vụ `{code,message}`; 400 dữ liệu/OTP sai, 401 thông tin xác thực sai hoặc phiên hết hiệu lực, 403 thiếu quyền/Origin, 409 thông tin đăng ký trùng, 429 giới hạn, 503 kiểm tra mật khẩu tạm lỗi. Lỗi tại security filter có HTTP 401/403; client chỉ tự refresh/retry khi 401 có challenge Bearer, không replay lỗi mật khẩu hiện tại từ controller.

| Endpoint | Input → output / quyền |
|---|---|
| POST `/auth/register` | `{name,studentId,email,password}` → 201 `{challengeId,expiresIn:300,resendAfter:60,message}`; công khai, không nhận role/điểm |
| POST `/auth/otp/resend` | `{email,purpose:"REGISTER" hoặc "RESET"}` → challenge cùng dạng; công khai, phản hồi chung cho email chưa có tài khoản |
| POST `/auth/otp/verify` | `{challengeId,email,purpose,code}` → `{resetToken,emailVerified}`; REGISTER chỉ xác minh email; RESET cấp grant một lần/5 phút |
| POST `/auth/login` | `{email,password,client:"mobile" hoặc "admin-web"}` → `{token,refreshToken,user}`; web cần Origin được phép và vai trò quản trị, refreshToken trong JSON bằng null, cấp cookie |
| POST `/auth/refresh` | Mobile `{client:"mobile",refreshToken}`; web `{client:"admin-web"}` + cookie/Origin → phiên mới; replay thu hồi family |
| GET `/auth/me` | Bearer hợp lệ → user hiện tại, kiểm phiên và quyền từ DB |
| PATCH `/auth/profile` | Bearer → chỉ `{name}`; từ chối email, userId và mọi trường ngoài hợp đồng; hồ sơ đầy đủ do P1-02 |
| POST `/auth/logout` | Bearer → 204, thu hồi phiên hiện tại; web kiểm Origin và xóa cookie đúng path |
| POST `/auth/password/change` | Bearer + `{currentPassword,password}` → token mới cho phiên hiện tại; các phiên khác bị thu hồi; web kiểm Origin |
| POST `/auth/password/reset` | `{resetToken,password}` → 204, thu hồi tất cả phiên và grant/challenge reset; đăng nhập lại |
| GET `/listings?offset=0` | Công khai → `{id,title,description,price,seller}[]`; chỉ CONG_KHAI, seller chỉ là tên hiển thị |

`user` gồm `id,name,email,studentId,role,roles,emailVerified,profileApproved,accountStatus`. `role` là nhãn UI `member/moderator/admin`, **không dùng để cấp quyền**; `roles` là quyền backend MEMBER/MODERATOR/SENIOR_ADMIN. Mobile không cấp quyền quản trị dù tài khoản có bản ghi vai trò. Web kiểm duyệt dùng `/admin/**`; thao tác cấp cao phải đặt dưới `/admin/senior/**`. Không giữ alias ADMIN. Đường health chuẩn là `/api/v1/health`.

Cookie refresh chỉ gửi tới `/api/v1/auth/refresh`; logout xác định phiên qua access token. CORS allowlist có credentials và expose `WWW-Authenticate` để trình duyệt đọc challenge hết hạn. Web/API dùng HTTPS cùng site khi triển khai; thử local bằng `localhost` cả hai origin (không trộn localhost với 127.0.0.1).

## Chính sách đã duyệt và lựa chọn triển khai

- OTP 6 số/5 phút, 5 lần sai/mã, resend 60 giây, 5 gửi/giờ và 10/ngày/email, 10 xác minh sai/giờ/email; gửi lại không xóa bộ đếm. Cửa sổ trượt theo UTC. HMAC-SHA256 lưu mã/token, AES-GCM chỉ bảo vệ payload cần gửi SMTP.
- Chống lạm dụng bổ sung: 100 request auth công khai/giờ/IP, dùng remote address trực tiếp, chưa tin X-Forwarded-For. Khi đặt reverse proxy phải cấu hình trusted proxy trước, tránh coi cả KTX là một người. Sau đăng nhập sai lần 5: chờ 30/60/120/240/480/900 giây; tối đa 15 phút. Sai mật khẩu hiện tại 5 lần/giờ thì chặn đổi trong cửa sổ, không khóa tài khoản giao dịch.
- Lưu và kiểm tra trạng thái session/generation ở DB; đổi mật khẩu tăng generation của phiên được giữ. Refresh token xoay vòng nhưng không kéo dài hạn tuyệt đối 30 ngày.
- Người chờ duyệt sửa hồ sơ mình và xem tin công khai. MEMBER chỉ có khi `email_verified=true`, `profile_approved=true`, trạng thái `HOAT_DONG`. Chưa có role thì API giao dịch bị 403. Duyệt hồ sơ không được thay bằng endpoint công khai.
- Chưa triển khai đổi email vì chưa có UC chi tiết; API hồ sơ từ chối sửa email trực tiếp. Chưa thêm MFA/passkey. Với BI_KHOA/VO_HIEU_HOA hiện từ chối phiên; quyền đọc/hoàn tất giao dịch/khiếu nại chi tiết cần P1-05/UC, không tự coi là đã triển khai.

## Cách thử lại

Cần Java 21, Node 24, Docker/PostgreSQL 16, Maildev. Cấp `JWT_SECRET` Base64 ngẫu nhiên tối thiểu 32 byte qua môi trường; `.env.example` không chứa khóa mẫu dùng được. Spring không tự đọc file `.env`; phải export biến hoặc cấp trong cấu hình IDE.

- Backend: tại `backend`, chạy Maven Wrapper `clean verify`. Testcontainers tự tạo DB; không bỏ integration test. Test dùng MailSender giả để kiểm lỗi/đồng thời, riêng lượt live dùng SMTP thật.
- Hai client: trong từng thư mục chạy `npm ci`, `npm run lint`, `npm test`, `npm run build`. Mobile build là export Android, không phải APK.
- Kiểm thử live dùng riêng container `p101-postgres` (user/db `p101`, password chỉ thử `p101-local-test`, host port 25432) và `p101-maildev` (SMTP 21025, HTTP 21080). Backend port 28082, CORS `http://localhost:25173`; web Vite port 25173 với `VITE_API_URL=http://localhost:28082/api/v1`. Không trỏ test fixture vào dữ liệu thật.
- Web: cài Playwright vào `.local/p1-tools` bằng npm với `--prefix`, rồi chạy `node scripts/verify-p1-01-web.cjs` từ root. Script mặc định dùng Edge cài trên Windows, tự đăng ký tài khoản thử và dùng SQL fixture trên **p101-postgres** để cấp vai trò; không dùng tài khoản seed có sẵn.
- Mobile live: đặt `EXPO_PUBLIC_API_URL=http://localhost:28082/api/v1`, `P1_MAILDEV_URL=http://localhost:21080`; chạy Jest với `--runInBand --testMatch '**/e2e/auth.live.tsx'` từ mobile. File này không tự chạy trong unit suite mặc định.
- Thiết bị: theo README mobile, dùng IP/port API thiết bị truy cập được; thử đăng ký → Maildev OTP → login → hồ sơ chờ duyệt → logout. Sau P1-02, bổ sung luồng duyệt thật → có quyền giao dịch.
